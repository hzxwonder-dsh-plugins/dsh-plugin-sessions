# 会话插件验证

环境：macOS、Node.js 24.11.1、DeepSeek Harness 0.1.5-rc.2。

`npm test` 通过 11 项测试，覆盖点击时的剪贴板授权与异步引用读取、原生引用编码与 Unicode 标题、对话工作区注册与顺序、已注册目录复用、名称配置、未知引用拒绝、原生界面适配的版本约束与稳定渲染、以及无工作区与带工作区两条新会话路由。

`node scripts/integration-check.mjs` 在临时 profile 和端口 3397 启动真实 Harness，通过以下项目：

- `/api/dsh-sessions` 的 `chat` 请求返回对话目录、工作区 id 与名称 `对话`，目录实际创建。
- 重复请求复用同一工作区，注册表按路径去重。
- 通过该工作区 id 创建的会话，其 `cwd` 是对话目录并计入该工作区成员。
- 同一实例内另一工作区排在其前，对话工作区位于列表末尾；重启后顺序不变且不重复注册。
- 目标会话的模型输入包含源会话内容和对应引用来源。
- 引用来源写入目标会话的持久化记录。
- 缺失会话返回错误，分叉与归档会话可以引用。
- 服务重启后，已归档源会话的内容仍能进入新会话的模型输入。
- 聊天记录由原有持久化服务管理。

模型输入检查使用本地确定性适配器，覆盖 Harness 实际消息组装与持久化路径。

界面检查在临时 profile 的真实 Harness 中通过浏览器完成：输入卡片的工作区标签显示 `对话`，输入框可用且不需要选择工作区；工作区会话的标签在鼠标悬停时显示 ⊗，点击后进入对话会话，对话模式下该控件不出现；左侧工作区列表渲染出 `对话` 分组并位于末尾，展开的工作区行提供 `在“<工作区>”中新建会话`；`uiWorkspace.startSession` 与浏览器宿主接口的可见行为与上述路由一致。

已应用适配的部署为全局安装 `~/.nvm/versions/node/v24.11.1/lib/node_modules/@deepseek-ai/dsh`（web profile）；适配写入 `client.js.dsh-sessions-backup.json` 备份，重启 Host 并刷新页面后生效。
